# Post-docking scientific audit

Audited commit: `cfe33056c77d817d19439a9e9affe225d00ca488`. Date: 2026-09-12. This is a source inspection and small adversarial execution audit, not an experimental accuracy benchmark. No pipeline code was changed. No applicable AGENTS.md was found in the repository or its immediate workspace ancestors.

## Assessment

The project has substantial orchestration and reporting infrastructure, but its current post-docking conclusions are not yet a reliable scientific decision layer. Several active calculations can reverse rankings or certify geometrically incorrect poses. Repair score semantics, pose identity, chemical identity, and validation denominators before adding more engines, images, or composite scores.

The canonical route is `workflow/execution.py` → `UnifiedPostDockingPipeline` → `MultiEngineAnalysisPipeline`. The unified `run()` executes the artifact DAG ([unified_pipeline.py, lines 232–248](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/unified_pipeline.py#L232)). The DAG directly calls the redocking validator, consensus builder, classifier, top-pose atlas, and ProLIF functions discussed below. Some older comparative/simplified analyses remain reachable in deeper/legacy routes; those are distinguished explicitly.

## Executed evidence

Run `python audit/postdocking_probes.py` from the repository root. Requires NumPy and pandas only. The script uses real module functions; the GNINA selector is executed from its unchanged AST method bodies to avoid importing optional visualization/docking stacks. Synthetic point sets isolate mathematical invariants; they are not molecular benchmark cases.

## Prioritized findings

### PD-01 — P1, confirmed: docking RMSD removes the positioning error it should measure

**Active default:** redocking gate and default `dockbox_geometric` consensus.

[`redocking_validation.py:115–143`](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/redocking_validation.py#L115) and [`geometric_consensus.py:214–227`](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/geometric_consensus.py#L214) center and rotate the **ligand itself** before measuring RMSD. Translating a ligand completely out of its pocket gives essentially zero. This assesses conformation after superposition, not recovery of the binding pose. The DAG uses that redocking result for its validation gate at [`multi_engine_pipeline_impl.py:576–594`](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L576). Default consensus grants geometric agreement an approximately 1.0 contribution, while rank contributes at most .001, so this incorrect result dominates ordering.

The two Kabsch implementations additionally form `V Uᵀ` but apply it to row-vector coordinates for a covariance `Aᵀ B`; a 90° rotation produces 3.12 Å instead of zero. Fixing that multiplication alone would still leave the more important scientific error above.

**Fix:** compare chemically mapped heavy atoms in the common receptor coordinate frame, with no ligand fitting. When receptors genuinely differ, align an explicitly selected receptor atom set and apply that transform to the ligand. Keep separately named `conformer_shape_rmsd` only where appropriate. RDKit's own `CalcRMS` documentation specifically distinguishes in-place docking RMSD from aligned `GetBestRMS` ([official RDKit source](https://raw.githubusercontent.com/rdkit/rdkit/master/Code/GraphMol/MolAlign/Wrap/rdMolAlign.cpp), `CalcRMS` documentation).

### PD-02 — P1, confirmed: score signs are inconsistent across selection, normalization, and export

**Active GNINA solo:** `_prepare_dag_consensus_inputs` chooses CNNaffinity then calls `_best_rows_by_group`, which always uses `idxmin` ([lines 672–703](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L672), [4719–4729](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L4719)). `_select_best_pose_rows` and `pose_extractor._is_better_pose` also minimize CNNaffinity. The consensus normalizer then assumes every input score is lower-is-better. GNINA CNNaffinity is predicted pK, while CNNscore assesses pose quality and normally ranks poses; both are higher-is-better ([GNINA primary paper](https://link.springer.com/article/10.1186/s13321-021-00522-2), molecular-docking pipeline and CNN-scoring sections). Selecting CNNaffinity rather than CNNscore can be an explicit experiment, but minimizing either is incorrect.

**Optional zscore mode:** [`consensus.py:157–164`](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/consensus.py#L157) negates z-scores, then calls a minmax helper that already inverts lower-is-better values. The double inversion reverses rankings.

**Optional weighted/strict atlas:** [`top_pose_selector.py:25–30,76–82`](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/top_pose_selector.py#L25) sorts weighted/strict consensus ascending, although the producer sorts every consensus mode descending. Smoke tests explicitly endorse the incorrect weighted direction ([test lines 2867–2876](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/test/test_dockforge_smoke.py#L2867)).

**All consensus modes:** `spread_norm` is built with a reversed minmax so small disagreement is high, then `(1-spread_norm)` is rewarded in geometric/strict/weighted, or `spread_norm` is subtracted in favorite mode ([consensus.py:314 onward](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/consensus.py#L314)). This rewards larger raw-score disagreement; in default geometric mode it affects the small tie-break term.

**Fix:** one immutable `ScoreSpec` with metric name, units, direction, scoring function/version, and task (pose selection versus ligand ranking). Every selector and normalization consumes it. Validate with monotonicity tests using physically correct positive CNN pK values; current negative CNN synthetic fixtures obscure the bug.

### PD-03 — P1, confirmed: selected pose and evaluated geometry can be different

**Active default redocking:** the loader retains the multi-pose source file plus a `pose` index ([GNINA lines 2455–2463](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L2455); Vina lines 2535–2543). `_compute_pose_rmsd` hardcodes pose 1; the PDB/PDBQT parser ignores MODEL boundaries entirely ([redocking lines 77–108,131–136](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/redocking_validation.py#L77)). Vina's usual multi-model output therefore gives atom-count mismatch against a single reference. GNINA can validate SDF pose 1 using the score of some other selected pose.

**Active default geometric:** splitting SDF on `$$$$` retains the separator newline at the beginning of the next record; the parser assumes the counts line is always `lines[3]` ([geometric lines 153–176](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/geometric_consensus.py#L153)). The second ordinary record fails. Out-of-range pose indices silently reset to pose 1 in both geometric parsers.

**Fix:** a single validated `PoseRef(source_hash, record_index, chemical_id, receptor_frame_id)` used for scoring, RMSD, interactions, and export. Reject missing/out-of-range records. Report Top1 and oracle/best-of-N validation separately; this implementation currently does neither consistently.

### PD-04 — P1, confirmed: atom-order guesses and missing engines can become geometric agreement

**Active default.** Equal atom counts plus an equal element sequence are accepted as correspondence, without bonds or symmetry mapping. For different-format atom-count mismatches of at most two, coordinates are sorted by distance from their own centroids, truncated, and compared; the result still contributes to valid/pass counts ([geometric_consensus.py:263–300](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/geometric_consensus.py#L263)). Missing heavy atoms are a chemical-identity failure, not a harmless output-format variation. Sorting by radius does not establish atom identity.

Engine files that fail parsing are dropped **before** calculating the expected pair count. With two readable agreeing engines and one absent file, the output says all pairs are within cutoff ([lines 374–436](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/geometric_consensus.py#L374)). This interacts badly with the SDF parser defect. The smoke test explicitly accepts 44-vs-43 heavy atoms as agreement ([test lines 3020–3047](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/test/test_dockforge_smoke.py#L3020)).

**Fix:** carry atom maps from preparation and validate graph identity and stereochemistry. Use allowed graph automorphisms for symmetry; retain failed/missing comparisons with the predeclared expected engine denominator. A shape-only partial comparison may be an exploratory feature, but cannot count as validated same-ligand agreement.

### PD-05 — P1, confirmed: reference identity and validation coverage are not trustworthy

**Active gate.** `bool(row.get("is_cocrystal_benchmark"))` treats NaN and the string `"False"` as true ([redocking_validation.py:47–63](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/redocking_validation.py#L47)). CSV missing values make this realistic. Reference discovery can then search ordinary raw/prepared ligand directories and accept fuzzy name matches, with no experimental-source or receptor-frame requirement ([lines 147–157,192–229](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/redocking_validation.py#L147)). A generated ligand conformer is not evidence of a native binding pose.

One evaluable pass among 100 intended references yields HIGH confidence and an open reference gate, because the confidence rule considers only pass/evaluable and no minimum independent sample size ([lines 415–457](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/redocking_validation.py#L415)). Multiple engine rows for one complex are also counted as separate evidence. The DAG classified-hits node never reads `allow_reference_anchor`; it loads baselines and applies the requested policy directly ([multi_engine_pipeline_impl.py:751–773](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L751)), unlike the older comparative report route, which checks that gate.

**Fix:** typed three-state flags; explicit experimental reference manifest (PDB/chain/residue/alternate location, ligand chemical identity, receptor frame, provenance hash); no fuzzy/raw-conformer fallback for validation. Report attempted/evaluable/pass separately by target, engine, preparation, and unique reference complex. Gate availability, coverage, and physical validity independently; define justified sample-size requirements instead of inferring high confidence from one row.

### PD-06 — P1, confirmed design defect: raw scores from different engines still determine winners and reference deltas

Within-engine normalization exists, but consensus also calculates `winner_engine=idxmin(raw_score)`, raw minimum/mean/spread, and rank of the raw minimum ([consensus.py:257–319](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/consensus.py#L257)). Raw minima select atlas identity rows and comparative rerun winners. Reference baselines choose the most negative passed result **across engines**, then discard engine identity during classification, comparing every candidate's cross-engine minimum with that value ([redocking lines 372–392](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/redocking_validation.py#L372); consensus reference-anchor block, lines 640 onward).

This is not repaired by labeling every number kcal/mol. AutoDock's official tutorial explicitly says AD4 and Vina scores are not comparable ([Vina documentation](https://autodock-vina.readthedocs.io/en/latest/docking_basic.html), section 5). An engine-specific offset can change the selected winner or reference classification without changing any engine's ligand ranking.

**Fix:** compare raw scores only within matched target/preparation/scoring-function/version conditions; reference deltas must retain the same engine and scoring function. Consensus should combine calibrated probabilities or within-condition ranks, with explicit missingness. `agreement_count` currently counts availability, not agreement in favorable rank; `strict_consensus` only requires at least two available scores. Rename coverage metrics and implement actual rank/pose agreement separately. Vina→smina→GNINA share ancestry, so three names must not be presented as three independent experimental confirmations ([GNINA repository](https://github.com/gnina/gnina)).

### PD-07 — P1/P2, strong source evidence; interaction stack not executed: exported PDB loses chemistry and sometimes receptor context

**Active explicitly requested interaction DAG branch:** The ordinary full/report scope does not schedule these optional interaction nodes; when requested, ProLIF receives the generated complex PDB via `create_interaction_map` ([multi-engine lines 952–986](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L952)). The GNINA OpenBabel export retains only receptor `ATOM` lines, rewrites every receptor chain as A, and retains only ligand coordinate lines, discarding connectivity ([pose_extractor.py:465–489](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/pose_extractor.py#L465)). Thus retained metal/cofactor HETATM records may be lost; chain identities can collapse. The fallback path preserves different receptor records, making context dependency-sensitive.

ProLIF reconstructs molecules from MDAnalysis with `NoImplicit=False`, without supplying authoritative ligand bond orders/formal charges, then calls the default fingerprint ([prolif_interaction_maps.py:375–405](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/prolif_interaction_maps.py#L375)). This is insufficient to guarantee aromaticity, charge, and donor/acceptor identity. Missing-ligand paths return True after making placeholder figures, so artifact success does not establish successful scientific analysis.

**Fix:** retain a validated selected-pose SDF with original graph/formal charge/atom map, plus receptor model and preserved cofactors; use the SDF-based supplier already present in the code. Use a supported explicit-H workflow or correctly standardized implicit-H interactions. ProLIF's own tutorials require chemical templates for PDB/PDBQT reconstruction and distinguish implicit-H fingerprints ([docking tutorial](https://prolif.readthedocs.io/en/stable/notebooks/docking.html), [PDB tutorial](https://prolif.readthedocs.io/en/latest/notebooks/pdb.html)). Report computation success, empty fingerprint, and failed chemical preparation separately. No claim is made here that every current map is wrong; specific chemical cases need RDKit/MDAnalysis/ProLIF execution.

### PD-08 — P2, confirmed: no physical-pose validity gate before “Strong”/QC pass

The default classifier initially assigns `qc_status=pass`; it only checks positive best affinity and low engine count ([consensus.py:699 onward](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/consensus.py#L699)). Geometric disagreement or unavailable geometry does not become a QC failure. `complex_validation.py` intentionally checks format and atom counts, not chemistry, clashes, bond strain, or pocket occupancy. Relative target percentiles can therefore award “Strong” to the best member of a wholly unsuccessful screening set.

**Fix:** preserve relative prioritization as a named rank label, and independently gate chemical consistency, receptor clashes, ligand strain, and placement. PoseBusters provides an existing open validation approach; its primary paper shows why RMSD alone is insufficient ([Buttenschoen et al.](https://pubs.rsc.org/en/content/articlelanding/2024/sc/d3sc04185a)). This is a missing capability, not evidence that a particular user's poses are physically invalid.

### PD-09 — P2, confirmed: optional biology merges duplicate candidates and can consume selection slots

`attach_biology_annotations` permits duplicate keys in a many-to-many left merge and computes matches/initial docking rows ([biology_integration.py:142–176](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/biology_integration.py#L142)). Two assay rows for one ligand yield two candidate rows and 200% matching. The comparative report route substitutes this expanded frame for consensus and reruns top-N selection ([multi-engine lines 2703–2725](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L2703)), so replicate assays can displace distinct candidates. Correlation code treats numeric annotations generically and counts repeated rows as paired observations.

**Fix:** keep assay observations in a separate table; validate merge cardinality, aggregate only explicitly matched assays/units/relations, and select distinct immutable pair IDs. Assay type, target, species, endpoint, units, inequality/censoring, and replicate identity must be explicit. Correlating arbitrary numeric annotations or pooled targets is exploratory, not validation of predicted affinity.

### PD-10 — P2, confirmed in deeper routes: global RMSD and polypharmacology exceed what these calculations establish

The optional per-protein/global RMSD bridge groups different ligands and passes them to an RMSD routine that checks only atom count and traversal order ([multi-engine lines 5575–5603](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/multi_engine_pipeline_impl.py#L5575); [enhanced_rmsd_analyzer.py:90–118](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/enhanced_rmsd_analyzer.py#L90)). Different same-sized molecules can obtain a numerical “pose RMSD”; different-sized molecules become missing. Neither is a chemically grounded cross-ligand pose comparison. Restrict RMSD to identical mapped ligand states in a common receptor frame; use explicitly defined pharmacophore/shape/interaction similarity for other comparisons.

The simplified deep-analysis polypharmacology route uses fixed −7/−5 thresholds, unvalidated name-based reference minima, an arbitrary weighted score, and target-count labels such as “High Polypharmacology Potential” ([simplified_pipeline_impl.py:1970–2035](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/simplified_pipeline_impl.py#L1970), [2072–2115](https://github.com/OASolliman590/OmniDock-Unified-Multi-Engine-Docking-and-Post-Docking-Analysis-Workflow/blob/cfe33056c77d817d19439a9e9affe225d00ca488/post_docking_analysis/simplified_pipeline_impl.py#L2072)). Missing/unattempted targets are not experimental negatives; equal percentile rank in two targets does not establish equal affinity or selectivity. Preserve a target×ligand matrix with attempted/failed/missing states and within-target uncertainty. Call outputs docking-based prioritization hypotheses until target-specific screening calibration and experiments support potency/selectivity claims.

## Redesign priorities

1. **First repair:** unify metric directions; remove ligand superposition from docking RMSD; eliminate truncation/missing-engine passes; fix multi-record selection; type reference flags and require native-pose provenance. Rerun existing result sets through the repaired analysis and issue an explicit artifact-version change.
2. **One scientific record model:** ligand parent/state/graph/atom IDs; receptor preparation/frame IDs; docking run/seed/engine/scoring function; pose record; score specification; validation result; assay observation. Use foreign keys, immutable hashes, and schema checks. Display names and paths are not identities.
3. **One pose validation layer:** chemistry + frame + physical validity + interaction recovery, with unavailable distinct from false and fail. Native validation is per target/protocol/engine, not one global pass-rate label.
4. **Benchmark before new composites:** curated cognate redocking, cross-docking to alternate receptor structures, repeated seeds, and held-out targets/ligands. Report Top1, best-of-N, physical-validity-adjusted success, coverage, confidence intervals, and known-active/decoy enrichment. Split homologous targets and analog series to prevent optimistic evaluation. Tune consensus on a development set and freeze it before external assessment.
5. **Use more independent evidence:** compare genuine scoring functions, validated interaction patterns, receptor-state sensitivity, and experimental endpoints. Estimate engine correlation; do not give closely related wrappers equal independent votes. More engines alone do not fix weak chemical preparation or invalid outcome definitions.

## Limitations and useful existing work

The project already records pose indices, keeps engine labels, provides configurable scopes, marks some unavailable outputs, separates ADMET labels from docking class, and blocks the old random structure-quality stage in the canonical workflow. Those are useful foundations. The random Ramachandran/clash functions in `structure_quality.py` are legacy placeholders and were **not** treated as active default scientific results in this audit.

No real docking, experimental-affinity benchmark, PLIP/PandaMap/ProLIF run, receptor conversion, or exhaustive route execution was performed. RDKit was unavailable in the inspected Python environment; no heavy dependency installation was undertaken. The probes directly establish algorithmic and dataflow failures, not their prevalence in historical user datasets. Primary documentation was accessed on 2026-09-12; dependency versions should be pinned before choosing exact repair APIs. Optional route bugs are labeled separately from the default DAG.
